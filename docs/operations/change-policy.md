# 契约变更与迁移政策

> **先判定，再修改。** 任何会让既有消费者无法读取、无法验证或改变既有含义的改动，都是破坏性变更。破坏性变更必须完成迁移准备，才能让 Codex 或 DeepSeek Harness 的消费者切换。

## 判断变更级别

| 类别 | 典型改动 | 处理方式 | 例子 |
| --- | --- | --- | --- |
| 向后兼容 | 新增可选字段，且不改变既有字段含义 | 保持 `schema_version`，补充有效样例和文档，再跑完整验收关卡。 | 为 `experiment.metrics` 增加一个可选数值指标。 |
| 破坏性变更 | 删除必填字段、改变字段类型、收窄枚举、改变 ID 模式或改变语义 | 先完成下面的迁移清单，再让消费者使用新对象。 | 把 `review-finding.severity` 从 `S0`–`S3` 改为另一套等级。 |
| 年度规则更新 | 新增或替换某届 `annual-rule` 的来源或条目 | 按规则溯源核验，并在变更影响语义时按破坏性变更处理。 | 将 2027 官方通知核验后加入规则集。 |

“可选”不等于可以悄悄改变含义。例如把已有 `status` 的解释从“运行结果”改为“审批结果”，即使字段未删除，仍是破坏性变更。

## 执行破坏性变更迁移

在任何消费者迁移前，维护者必须完成全部事项：

1. 为新协议发布新的 `schema_version`，并说明旧版本到新版本的字段映射。
2. 提供可重复运行的迁移脚本；脚本输入旧对象，输出符合新 Schema 的对象或明确失败。
3. 保留旧版与新版 fixtures，分别覆盖有效输入和命名原因明确的无效输入。
4. 执行 Codex 与 DeepSeek Harness 的 **双端契约回归**：两端均要读取新旧 fixtures，并验证迁移后的输出。
5. 更新 [契约参考](../architecture/contracts.md)、验收说明及面向使用者的文档。
6. 在消费者迁移前发布 release note，说明破坏点、迁移脚本位置、弃用期和回退方式。

例如，若 `artifact.path` 将来改为对象而不是字符串，不能只改 Schema；必须先发布新 `schema_version`、提供字符串到对象的迁移脚本、用旧/新 `artifact` 样例做双端契约回归，并在 release note 给出升级时间。

## 区分两个版本字段

| 字段 | 作用 | 何时改变 | 示例 |
| --- | --- | --- | --- |
| `schema_version` | 所有契约对象的协议版本，决定 Schema 与消费者解释方式。 | 发生破坏性变更时。 | `"schema_version": "1.0"` |
| `manifest_version` | 仅 `asset-manifest` 的清单组织版本，描述资产列表结构。 | 清单结构本身发生版本化变更时；若也影响消费者兼容性，仍需同步处理 `schema_version`。 | `"manifest_version": "1.0"` |

因此，改变资产清单结构时不能只提高 `manifest_version` 来规避迁移；只要 Codex 或 DSH 对对象的解释不再兼容，就需要新的 `schema_version` 和完整迁移流程。

## 核验年度规则来源

`annual-rule` 不是从网络自动抓取的事实。更新前必须记录官方或可审计来源 URL、核验时间和人工核验结论，确认年份、条款文字、强制方式和阻断属性都能回溯。完成溯源核验后，再运行 [Phase 0 验收关卡](../quality/acceptance-gates.md)。

例如，不能把 [现有 2026 synthetic example](../../shared/fixtures/contracts/valid/annual-rule.json) 当作赛事通知；它只测试格式。真实规则条目应由核验人从可复查来源转录，并保留更新理由与证据。
